# Documents 组件设计

> Starter Kit 四组件之一。前置：[`README.md`](README.md) · [`../../agent/architecture.md`](../../agent/architecture.md)
> 版本：v0.1 · 2026-09-05

## 1. 它到底是个什么东西

不是「文档 AI」这种空话。**它是六个具体动作**，每个有明确的输入输出：

| 动作 | 输入 | 输出 | 典型客户场景 |
|:---|:---|:---|:---|
| **summarize** | 一份长文档 | 结构化摘要（要点 / 决议 / 待办） | 30 页会议记录 → 一页纪要 |
| **extract** | 文档 + 字段定义 | 结构化数据（JSON/表格） | 100 份发票 → 一张对账表 |
| **compare** | 两份同类文档 | 差异清单（增/删/改，含风险标注） | 新旧合同版本对比 |
| **translate** | 文档 + 目标语言 | 保留格式的译文 | 泰文合同 → 英文，给外方看 |
| **rewrite** | 文档 + 目标语气/受众 | 改写后的文档 | 内部技术说明 → 客户能看懂的版本 |
| **search** | 一个问题 | 答案 + 出处（哪份文件第几页） | 「去年跟这家的报价是多少？」 |

**这六个不是随便挑的。** 它们对应 Discovery 里最常出现的六类重复劳动
（见 `../discovery-sop.md` §5.2 第 3–6 题问出来的东西）。

### 边界：它不是什么

- **不是知识库产品。** 我们不做「把你全公司文档灌进去」——那是个无底洞，
  且第一批客户的文档根本不成体系。`search` 的范围是**客户当次指定的一批文件**。
- **不是 OCR 产品。** 扫描件识别用 Docling 自带能力，不做优化，不承诺准确率。
- **不做文档编辑器。** 输出交回客户现有工具（Word / Google Docs / 邮件）。

## 2. 开源基座

| 组件 | 版本 | License | 它负责哪一段 |
|:---|:---|:---|:---|
| **Docling** | `2.x` | MIT | 文件 → 结构化中间表示（PDF/DOCX/PPTX/XLSX/图片 → 带布局的文档树） |
| **iDoris Gateway** | 自建（LiteLLM 基座） | Apache 2.0 / MIT | 模型调用、路由、成本闸、审计 |
| **pgvector** | `0.7+` on Postgres 16 | PostgreSQL License | `search` 动作的向量检索 |

> **License 状态**：Docling MIT **[待核：确认 2.x 主分支 LICENSE 文件与 PyPI
> 元数据一致]** · pgvector PostgreSQL License **[待核]** · 尽调结论见
> [`../oss-due-diligence.md`](../oss-due-diligence.md)。

**为什么是 Docling 而不是 Unstructured**：Docling 对**表格结构**和**扫描件版面**
的还原更好，而泰国 SME 的文档恰恰大量是「扫描的 PDF 里有表格」。
License 也更干净（MIT vs Apache 2.0 + 部分模型的额外条款）。

**为什么 `search` 用 pgvector 而不是 Qdrant/Milvus**：第一批客户的文档量在
几千到几万页级别，一个 Postgres 完全撑得住。**少一个要运维的东西**，
比多一点检索性能重要得多。等真的撑不住再换——换的成本远低于现在多养一个服务。

## 3. 我们自己写什么

开源件给的是**能力**，不是**产品**。我们写的是这三层：

### 3.1 中间表示（DocIR）

Docling 的输出是它自己的数据结构。我们在它之上定义一个稳定的中间表示，
**六个动作全部只依赖 DocIR，不直接依赖 Docling**：

```jsonc
{
  "doc_id": "sha256:...",
  "source": {"filename": "quote-2026-08.pdf", "mime": "application/pdf", "pages": 3},
  "lang_detected": ["th", "en"],          // 泰英混排是常态
  "blocks": [
    {
      "id": "b1", "type": "heading|paragraph|table|list|figure",
      "page": 1, "bbox": [x0, y0, x1, y1],   // 出处回溯要用
      "text": "...",
      "table": {"rows": [[...]], "header": true}   // type=table 时才有
    }
  ]
}
```

**为什么要这一层**：Docling 换版本、甚至整个换掉，六个动作的代码都不用动。
这是**唯一一处值得我们自己造轮子的地方**——它是隔离层，不是重复实现。

`bbox` 与 `page` 必须保留：`search` 要回答「在哪份文件第几页」，
`extract` 要让客户能点回原文核对。**没有出处的抽取结果没人敢用。**

### 3.2 六个动作的 Skill 封装

每个动作 = 一个提示词模板 + 一个输出 schema + 一条路由规则。

| 动作 | 路由到哪档模型 | 为什么 |
|:---|:---|:---|
| translate | 低价档 | 翻译对模型能力要求最低，量最大 |
| extract | 低价档 + `strict` schema | 结构化输出，schema 约束比模型智商重要 |
| summarize | 中档 | 需要判断什么是要点 |
| rewrite | 中档 | 语气把握 |
| compare | **高档** | 漏掉一条合同差异的代价很高 |
| search | 低价档（检索）+ 中档（作答） | 检索靠向量，作答才用模型 |

这张表是 Gateway 路由策略的具体实例，也是「省钱来自选对模型」这句话的兑现物。

### 3.3 泰文文档的三个坑（这是本地化的真实内容）

1. **泰文没有词间空格。** 常规分词器会把整句切成一块，导致
   `search` 的向量检索召回极差。**对策**：切块时对泰文段落用
   句子边界（`ๆ`、`।`、换行、标点）而非空格；块大小按**字符数**不按词数。
2. **泰文 PDF 的字形重排。** 部分泰文 PDF 提取出来元音符号与辅音顺序颠倒，
   肉眼看着对、字符串比对全错。**对策**：提取后做 Unicode NFC 归一化，
   并在 `extract` 的 schema 校验里对泰文字段放宽精确匹配。
3. **泰英混排的语言检测。** 一份文档里泰英交替是常态，整篇检测语言会误判。
   **对策**：`lang_detected` 是数组不是单值，按 block 检测。

> 这三条是**真的会踩到的**工程细节，不是凑数。它们决定了 Documents
> 在泰国能不能用——也正是「本地化不是翻译」这句话的具体含义。

## 4. 六个动作的具体设计

上面那张路由表只说了「用哪档模型」。这里说每个动作**具体怎么做、坑在哪**。

### summarize — 摘要

- **提示词策略**：先让模型标出文档类型（会议记录/合同/报告），再按类型套不同的
  输出骨架。通用摘要对会议记录会漏掉「谁承诺了什么」。
- **输出 schema**：`{key_points[], decisions[], action_items[], open_questions[]}`
- **坑**：长文档要分块摘要再合并，合并时容易丢掉跨块的因果关系。
  **对策**：合并阶段把各块的 `decisions` 和 `action_items` 全量带上，只压缩 `key_points`。
- **验收**：抽 10 份客户真实文档，人工判「摘要里有没有漏掉重要决议」，≥8 份通过。

### extract — 结构化抽取

- **提示词策略**：必须给 `strict` schema，让模型只填字段不自由发挥。
- **输出 schema**：客户定义。每个字段附 `citation`（`doc_id` + `page` + `bbox`）。
- **坑**：数字与日期最容易错——泰历（佛历）年份比公历多 543 年，
  客户文档里两种都有。**对策**：日期字段强制要求模型同时输出原文串与解析值，
  由我们的代码判断历法并转换，**不让模型自己算**。
- **验收**：抽 50 条字段，逐条点开 citation 核对，准确率 ≥95%（数字字段 100%）。

### compare — 文档对比

- **提示词策略**：先对齐结构（按条款号/小节标题），再逐段比对。
  直接把两份全文丢给模型比对，会漏掉顺序调换的条款。
- **输出 schema**：`{added[], removed[], modified[{before, after, risk_note}]}`
- **坑**：**这是六个动作里唯一「漏一条就可能造成损失」的**，所以路由到高档模型，
  且输出必须逐条带双向 citation（新旧各指一处）。
- **验收**：人工构造 10 处差异（含 2 处顺序调换、2 处数字微调），全部要被找出。

### translate — 翻译

- **提示词策略**：按 block 翻译而非整篇，保留 DocIR 的结构，最后重组。
  整篇翻译会丢掉表格和版式。
- **坑**：泰英互译中，**人名、公司名、地名不该翻**。
  **对策**：先跑一遍实体识别标出专有名词，翻译时指示保留原文并在括号内附译名。
- **坑**：泰文敬语体系（ครับ/ค่ะ 及层级用词）译成英文会全丢，反向则容易用错。
  **对策**：`params.formality` 显式指定，默认商务正式。
- **验收**：泰英各 20 段，母语者判「能不能直接用」，≥16 段通过。

### rewrite — 改写

- **提示词策略**：输入必须带 `target_audience` 与 `tone`，二者缺一不做——
  没有目标受众的「改写」是没有判据的。
- **坑**：模型倾向于把内容变长。**对策**：提示词里给出长度约束，
  输出后校验，超出 120% 就重跑一次。
- **验收**：改写后的事实性内容不得增减（人工抽查 10 份，不得出现原文没有的数字或承诺）。

### search — 检索问答

- **提示词策略**：先向量检索取 top-k 块，再让模型基于这些块作答，
  **明确指示「资料里没有就说没有」**。
- **坑**：泰文分块（见 §3.3 第 1 条）直接决定召回质量，这是 `search` 最大的风险点。
- **坑**：客户会问超出文档范围的问题。**对策**：无命中时直接回「这批文件里没有」，
  不允许模型用通用知识补。
- **为什么排最后做**：它是六个里唯一「做不好会砸招牌」的——
  一个自信地答错的检索系统，比没有检索系统更糟。
- **验收**：构造 20 个问题（其中 5 个答案不在文档里），
  20 题全对且那 5 题都要如实回答「没有」。

## 5. 接口

```
文件 ──Docling──> DocIR ──动作 Skill──> 结果
                    │                      │
                    └──分块+嵌入──> pgvector ┘（仅 search）
```

**对外只暴露一个入口**：

```
POST /documents/{action}
  action: summarize | extract | compare | translate | rewrite | search
  body:   { doc_ids: [...], params: {...} }
  → { result: ..., citations: [{doc_id, page, bbox}], usage: {model, tokens, cost} }
```

`citations` 与 `usage` **两个字段都是必填**：前者让客户能核对，
后者让客户看见每次调用花了多少钱（Gateway 的审计留痕在页面上的体现）。

## 6. 最小可用形态（先做哪两个）

**先做 `extract` 和 `translate`，其余四个排后面。**

理由：

- 这两个**演示效果最直接**：客户拿自己的一份泰文发票/合同过来，
  当场看到结构化表格和英文译文，不需要任何解释。
- 这两个**技术风险最低**：不依赖向量库（`search` 才需要），
  不依赖高档模型（`compare` 才需要）。
- 这两个**恰好覆盖 Discovery 里最常见的两类痛点**：数据搬运、跨语言沟通。

`search` 排最后——它需要 pgvector、需要分块策略调优、需要客户先把文档给全，
是四个里唯一一个「做不好会砸招牌」的。

## 7. 怎么演示给客户看

**5 分钟脚本**（写死，不要临场发挥）：

1. 让客户**当场**给一份他们自己的泰文文档（发票 / 报价 / 合同）。
2. 跑 `extract` → 出结构化表格。**指着某一行说「这个数字在第 2 页这里」**
   （点开 citation）。
3. 跑 `translate` → 出英文版，格式保留。
4. **指出一处它做得不够好的地方**，说明为什么、以及怎么补。
5. 说明这次调用花了多少钱（`usage` 字段），大约是 0.0X 美元。

第 4 步是关键。主动指出局限，比多演示两个功能有用得多——
参见 `../discovery-sop.md` §3 交付会的第五步。

## 8. 风险

| 风险 | 影响 | 对策 |
|:---|:---|:---|
| 泰文 PDF 提取质量不稳定 | 演示翻车 | 演示前用客户文档预跑一遍；准备降级话术 |
| 扫描件质量差 | 抽取结果不可用 | 明确不承诺 OCR 准确率，Readiness 评分里体现 |
| 客户要求「全公司文档搜索」 | 范围失控 | 边界写死：`search` 只对当次指定的一批文件 |
| Docling 大版本变更 | 全部动作受影响 | DocIR 隔离层就是为此存在 |
