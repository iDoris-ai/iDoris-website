# Voice 组件：现状盘点与补齐设计

> 四组件里**唯一已有基础**的。所以这份文档的任务不是从零设计，
> 而是回答两个问题：**现在到什么程度了？缺什么才能当产品演示？**
> 版本：v0.1 · 2026-09-05

## 1. 现状盘点

> ⚠️ **[待核]** 本节内容基于源文档「你已经有：Thai / English / Chinese Voice Input」
> 这一句，**尚未核实代码现状**。
> **核法**：在 iDoris 的代码仓库里确认——① 用的是哪个 whisper 实现与模型尺寸；
> ② 泰语识别是否单独调过；③ 有没有可跑的 demo 入口；④ 部署形态（本地/云）。
> **谁核**：Dev，进入 T2.2.1 实现前的第一件事。
>
> **在核清楚之前，下面的「缺什么」是基于通用 whisper 能力的推断，不是对现状的断言。**

## 2. 它在 Starter Kit 里的角色

Voice 不是一个独立卖点，**它是入口**：

```
语音 ──Voice──> 文字 ──┬──> Documents（整理成文档）
                       └──> Assistant（会议 → 纪要 → 任务）
```

Discovery 现场自己也在用它（访谈录音转写，见 `../discovery-sop.md` §0.4）——
**我们自己每天用的东西，演示时最有说服力。**

## 3. 开源基座

| 组件 | License | 负责哪一段 |
|:---|:---|:---|
| **faster-whisper** | **[已核 2026-09-06]** MIT（GitHub API：`SYSTRAN/faster-whisper` SPDX = MIT）| 语音 → 文字（CTranslate2 后端，比原版 whisper 快数倍且省显存） |
| CTranslate2 | **[已核 2026-09-06]** MIT（GitHub API：`OpenNMT/CTranslate2` SPDX = MIT）| 推理运行时 |
| Whisper 模型权重 | **[已核 2026-09-05]** MIT（`Systran/faster-whisper-large-v3`，HuggingFace API；`openai/whisper-large-v3` 原始权重为 Apache-2.0）| 实际识别 |

**三层全部可商用，无附加条款。** 代码、运行时、权重的许可是**三件独立的事** ——
代码 MIT 不代表权重可商用，这一条在 `oss-due-diligence.md` 里已经吃过一次亏。

### ⚠️ 但许可干净 ≠ 可以放心用

**[已核 2026-09-06]** `faster-whisper` **维护者已停更 9 个多月**
（最后提交 2025-11-19），而它的推理后端 `CTranslate2` **仍在活跃发版**
（v4.8.2 · 2026-08-31）。CUDA 兼容问题从 2024-10-24 open 至今，
修复 PR 于 2026-04-13 **被关掉未合并**。

**风险不是「哪天它坏了」，是「它已经在坏，只是我们还没装」** ——
后端每发一版，兼容缺口就宽一点，而没有人在补。

**决定：不换方案，但必须①同时锁两个包的版本、②部署时显式验 GPU 路径**
（那个报错在 import 阶段不出现，跑起来才出现）。
完整证据见 [`../verification-2026-09-06-voice-stack.md`](../verification-2026-09-06-voice-stack.md)，
执行步骤见部署 Runbook §2.3.1（在 PR #48 里，尚未合并）。

**为什么本地跑而不是云 API**：泰国客户的会议录音包含大量敏感内容
（人事、报价、客户信息）。**「你的录音不出你的机器」是卖点，不是成本负担**——
这一条在 Readiness 评分的「治理准备」维度上直接加分。

## 4. 缺什么（补齐清单）

### 4.1 泰语识别质量：先建立评测，再谈优化

**不能凭感觉说「泰语识别还行」。** 需要一个可重复的评测：

| 项 | 做法 |
|:---|:---|
| 测试集 | 录 20 段真实场景音频：会议室（多人）、电话、嘈杂环境（餐厅/大堂）各若干 |
| 参考文本 | 人工转写作为 ground truth |
| 指标 | **CER（字符错误率）**，不用 WER —— 泰文没有词间空格，WER 不适用 |
| 分层报告 | 按场景分开报，别给一个平均数掩盖问题 |

**这个评测本身就是交付物**：向客户展示「我们测过，在你这种场景下大概 X%」，
比说「支持泰语」有力得多。

### 4.2 泰英中混合输入

真实场景是**一句话里混着两三种语言**（泰国办公室的常态）。
whisper 的 `language` 参数是单值，指定了会把其他语言硬套。

**对策**：分段检测 + 分段识别，输出按段落标注语言
（与 Documents 的 `lang_detected` 是数组同一个思路）。

### 4.3 说话人分离（Diarization）

会议纪要要区分「谁说的」，否则 Assistant 抽不出任务负责人。

**决策：第一版不做。** 理由——说话人分离要额外引入 pyannote 之类的依赖，
其模型权重许可需单独核（部分要求接受 HuggingFace 的条款），
且多人会议的准确率不稳定。

**替代方案**：录音时手动标注参与者名单，Assistant 在抽任务时
用「按语境推断 + 人工审批时确认负责人」。**审批环节反正要人看，
让人顺手确认负责人，比强行做说话人分离划算。**

### 4.4 语音 → 文档模板的衔接

现在是「出一坨转写文字」。要变成产品，需要：

```
转写稿 ──> 选模板 ──> 结构化文档
              ├── 会议纪要（议题/决议/待办）
              ├── 访谈笔记（Discovery 用，直接填 pain-inventory）
              └── 口述草稿（邮件/报价）
```

**「访谈笔记」这个模板优先做**——它是我们自己 Discovery 时每天要用的，
自己天天用的东西最不容易做歪。

## 5. 最小可用形态（演示级）

**一条端到端**：泰语会议录音 → 转写（标注语言段落）→ 会议纪要模板 → 交给 Assistant 抽任务。

**演示脚本**：
1. 当场录 2 分钟泰英混杂的对话
2. 展示转写，指出哪几段是泰语哪几段是英语
3. 出会议纪要
4. **说出评测数据**：「我们在类似环境测过 20 段，字符错误率大约 X%」
5. **指出局限**：嘈杂环境会明显变差；不区分说话人

第 4 步是 Voice 区别于「随便一个转写 App」的地方——**有测过的数字**。

## 6. 风险

| 风险 | 影响 | 对策 |
|:---|:---|:---|
| 现状与假设不符 | 整个 Starter Kit 演示计划要改 | **T2.2.1 第一件事就是核现状**，不要在假设上继续叠设计 |
| 泰语 CER 高到不可用 | Voice 不能当入口 | 先建评测再定去留；不行就降级为「英语可用，泰语标注为实验」 |
| ~~模型权重许可~~ | ~~商用风险~~ | **[已核 2026-09-05/06] 三层全部 MIT，可商用**（见 §3）。**Creative 的图像权重仍 [待核]** —— 那是另一件事，不要混在一起说 |
| **上游停更** | 兼容缺口随后端发版变宽 | **[已核 2026-09-06]** 锁版本 + 显式验 GPU 路径（见 §3） |
| GPU 成本 | 本地部署门槛 | large-v3 可在 CPU 跑但慢；第一批客户用我们托管 |
