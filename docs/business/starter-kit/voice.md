# Voice 组件：现状盘点与补齐设计

> 四组件里**唯一已有基础**的。所以这份文档的任务不是从零设计，
> 而是回答两个问题：**现在到什么程度了？缺什么才能当产品演示？**
> 版本：v0.2 · 2026-09-07（V0 盘点已完成，§1/§3/§4.1/§6 整体重写，新增 §7）

## 1. 现状盘点

> ✅ **[已核 2026-09-07]** 完整证据与可复现命令见
> [`../verification-2026-09-07-voice-v0.md`](../verification-2026-09-07-voice-v0.md)。

**「已有基础」是真的 —— 但基础不在我们以为的地方，也不是我们以为的技术栈。**

它在 [`iDoris-ai/AgentEar`](https://github.com/iDoris-ai/AgentEar)：
一个已发布 `.app` 的 macOS 常驻程序（v0.4.2 · 2026-09-03）。
**M1（按键即录即转写）完成；M2（理解层：术语纠错 + 标签路由）已建但默认关**
—— 它要用户自备一个本地 LLM，不启用也不影响转写。
iDoris 主仓库那 24 个文件**全是文档，零代码**——所以在那里是找不到的。

原来要核的四问，逐条回答：

| 问 | 答 |
|:---|:---|
| 哪个 whisper 实现与模型尺寸 | **不是 whisper。** 主链路是 SenseVoiceSmall q8 GGUF（242 MiB）+ FunASR llamacpp runtime + fsmn-vad |
| 泰语单独调过没 | **调过，而且是另一条独立引擎** —— SenseVoice 不支持泰语，泰语走 whisper.cpp + 显式指定语言（不是自动检测），有 ADR 固定模型指纹 |
| 有没有可跑的 demo | **有发布版 `.app`**（[已核]：Releases 页上确实有）。性能数字（7.4 秒录音全程 7.8 秒、空闲常驻 13 MB）是 **[AgentEar 自述]** —— **我们没有安装复测过** |
| 部署形态 | 本地离线运行（**[AgentEar 自述]**，我们没做过断网探测）；**有官方产物的只有 Apple Silicon Mac** —— 见 §7 |

**四个答案没有一个和原来的假设一致。所以下面几节整体重写过了。**

> ⚠️ **证据分三档，别混读**：**[已核]** = 我们跑过命令看到输出；
> **[AgentEar 自述]** = 他们文档这么写、**我们没复测**；**[待核]** = 没有证据。
> **凡「能不能跑起来」的结论，我们目前一律不是 [已核]** —— 没装过。

### ⚠️ 但最要紧的一条不在这张表里：**AgentEar 不是我们的 Voice 实现**

**[jason 2026-09-07 定位]**：

> **AgentEar 是外部输入法组件**，未来还包括**独立的、可以插入到任意 agent
> 的「说话器官」**。

**这句话改变的是关系，不是事实**：我们不是「在 AgentEar 里找到了自己的代码」，
我们是**它的消费者**。含义有三条，每条都会影响做法：

| | 含义 |
|:---|:---|
| **不要把它当我们的私有实现改** | 它有自己的产品方向（输入法 → 说话器官），不会为 Starter Kit 的排期让路。我们提需求，不是提 commit |
| **许可要按外部依赖那样对待** | §3 那几张许可表不是走过场 —— 正因为它是外部组件，`NOTICE` 与再分发义务才是真义务（见 §3.2 的陷阱）|
| **「说话器官」是双向的** | 现在盘的是**听**（ASR）。AgentEar 已有 TTS 选型 ADR（`0005-tts-selection.md`）—— 意味着 Voice 这条线**将来不止是入口，还可能是出口**（Assistant 的审批结果念出来）|

**所以 §2 那张「Voice 是入口」的图，将来要加一条回来的箭头** ——
但那是 V3 之后的事，现在不动，**记在这里免得忘**。

## 2. 它在 Starter Kit 里的角色

Voice 不是一个独立卖点，**它是入口**：

```
语音 ──Voice──> 文字 ──┬──> Documents（整理成文档）
                       └──> Assistant（会议 → 纪要 → 任务）
```

Discovery 现场自己也在用它（访谈录音转写，见 `../discovery-sop.md` §0.4）——
**我们自己每天用的东西，演示时最有说服力。**

## 3. 开源基座 —— 两条链路，不是一条

**这是最容易搞混的一点**：主链路和泰语走的是**完全不同的引擎**，
不是「一个模型顺带支持多语言」。

### 3.1 主链路（中/英/日/韩/粤）

| 组件 | License | 负责哪一段 |
|:---|:---|:---|
| **SenseVoiceSmall q8 GGUF** | **[已核 2026-09-07]** Apache-2.0（242 MiB）| 语音 → 文字 |
| **FunASR llamacpp runtime** | **[已核 2026-09-07]** 取上游**发布产物**，tag 形如 `runtime-llamacpp-v0.2.6` | 推理运行时，单二进制零 Python |
| **fsmn-vad GGUF** | 同上游 | 静音切分 |

选型有 ADR（AgentEar `docs/decisions/0001-asr-model-selection.md`），
**四模型实测横比**，不是拍脑袋。关键权衡值得记住：

> **CER 四家相差不到 1 个百分点 —— 准确率根本区分不出来，差异全在工程形态。**
> SenseVoice 常驻内存是 Fun-ASR-Nano 的 27%、冷启动 0.2s vs 11.45s、单二进制零 Python。

**这个形状对我们特别有用**：客户机器上跑的东西，内存和冷启动比小数点后一位的准确率重要得多。

### 3.2 泰语支线（独立引擎）

| 组件 | License | 说明 |
|:---|:---|:---|
| **whisper.cpp** | MIT | 复用单二进制，无新运行时 |
| **`distill` q5_0 GGML** | **[已核 2026-09-07]** MIT（上游 `biodatlab/distill-whisper-th-large-v3`）| 峰值 RSS 712 MB；由 app 按需下载，不打进包 |

> 🔴 **三个泰语候选的上游许可不一样，这是个陷阱**：
> `distill` / `turbo` 是 MIT，但 **`medium` 是 Apache-2.0** ——
> 换成它 **NOTICE 义务要重新过一遍**（ADR-0004 原话）。
> 而 `medium` 恰好是 CER 表里最好的那个（6.08%）。
>
> **别上钩**：那 0.14 个百分点**未检出差异**（配对 CI [−0.0142, +0.0099]），
> 换它还要多付 425 MB 内存。**默认跟随 `distill` q5_0** ——
> 只有 §4.1 的真实场景评测里拉开**可检出**的差距才谈换，
> **而那时第一件事是重核 NOTICE，不是先上线。**

**为什么必须分开**：SenseVoice 的语种标记集里**根本没有 `th`**。
AgentEar 实测两次，泰语音频被标成 `<|en|>` / `<|yue|>`，输出是乱码。
所以泰语**显式指定语言**，不走自动检测。

> ⚠️ ADR-0004 把这条标为「**先用起来、拿到数据再复评**」的默认值，不是终局。
> 换模型的成本已经压到最低（改四个常量 + 重跑一个脚本）。

### 3.3 ⚠️ 许可干净 ≠ 可以放心用：上游风险换了对象

**原来记的「faster-whisper 停更 9.5 个月」那条风险，对主链路不适用了**
——我们的主链路根本不用它。
`../verification-2026-09-06-voice-stack.md` 的结论**本身仍然成立**，
但适用范围降级为「泰语支线的相邻生态」。

**风险没消失，换了个形状**：主链路依赖 `modelscope/FunASR` 的
**runtime 发布产物**，而不是自己编译。**产物停发 = 主链路断供。**

**对策与原来同形**：锁版本 + **自己留一份产物副本**（这条比锁版本更要紧
——锁住的版本号在上游删 release 之后是一句空话）。

> 📌 **一条被来件写错、我们核掉的**：「SenseVoice-Small 官方标注即将停止维护」
> **不成立**。那是厂商博客的二手说法，AgentEar 自己的 ADR-0001 已经更正过
> （GitHub 未 archive、最后提交 2026-07-27、HF 下载量高于对手）。
> **教训**：被 ADR 更正过的旧文档还躺在原地，引二手结论前先看有没有人改过它。

**为什么本地跑而不是云 API**：泰国客户的会议录音包含大量敏感内容
（人事、报价、客户信息）。**「你的录音不出你的机器」是卖点，不是成本负担**——
这一条在 Readiness 评分的「治理准备」维度上直接加分。
**但这句话有平台前提**，见 §7。

## 4. 缺什么（补齐清单）

### 4.1 泰语识别质量：不是从零建评测，是补他们没测的那一层

**[已核 2026-09-07] AgentEar 已经有泰语 CER 数字，而且是两批。**

| 语料 | n | 结果 |
|:---|---:|:---|
| FLEURS **朗读**语料 | 80 | 最好 `medium` q8_0 **CER 6.08%**，95% CI [4.41%, 7.89%]，自助法 4000 次 |
| code-switch 语料 | 22 | 纯泰对照 **3.9%**；泰语夹英文 **31.1%**；加一段 initial prompt 降到 **18.4%** |

夹英文的失败是**系统性的**：39 个英文词里 36 个被音译成泰文字母，不是随机错。
**所以「泰语识别质量」这件事的瓶颈不在模型，在 prompt** ——
这一条直接省掉我们本来要花在选型上的时间。

#### ⚠️ 但这些数字**不能写进销售话术**

两个理由，都得记住：

1. **是朗读语料，不是我们客户的场景** —— 安静、单人、念稿。
   会议室多人、电话、餐厅/大堂噪声，**两批都没测**。
2. **有污染，AgentEar 自己标注了**：FLEURS 被 Thonburian
   （`medium`/`distill` 的出处）的模型卡**声明为训练数据**。
   模型可能见过这批题。

**所以 §4.1 原来那个评测照做，一段都不减** —— 它测的正是他们没测的那一层：

| 项 | 做法 |
|:---|:---|
| 测试集 | 录 20 段真实场景音频：会议室（多人）、电话、嘈杂环境（餐厅/大堂）各若干 |
| 参考文本 | 人工转写作为 ground truth |
| 指标 | **CER（字符错误率）**，不用 WER —— 泰文没有词间空格，WER 不适用 |
| 分层报告 | 按场景分开报，别给一个平均数掩盖问题 |
| **对照组** | **加录几条安静环境朗读** —— 用来和 AgentEar 的 3.9% 对齐，确认我们的管道没跑歪 |

**变便宜的部分**：不用自己造轮子，AgentEar 那边可直接复用
`scripts/cer-thai.py`、`scripts/cer-stats.py`（含自助法 CI 与配对比较）、
`reference.tsv` 的 ground-truth 格式、以及 `docs/thai-recorder.html` 采录页。

**这个评测本身就是交付物**：向客户展示「我们测过，在你这种场景下大概 X%」，
比说「支持泰语」有力得多。**而且这个数字目前没有第二个人有。**

### 4.2 泰英中混合输入

真实场景是**一句话里混着两三种语言**（泰国办公室的常态）。
whisper 的 `language` 参数是单值，指定了会把其他语言硬套。

**对策**：分段检测 + 分段识别，输出按段落标注语言
（与 Documents 的 `lang_detected` 是数组同一个思路）。

### 4.3 说话人分离（Diarization）

会议纪要要区分「谁说的」，否则 Assistant 抽不出任务负责人。

**决策：第一版不做。** 理由——说话人分离要额外引入 pyannote 之类的依赖，
其模型权重许可需单独核（部分要求接受 HuggingFace 的条款），
且多人会议的准确率不稳定。

**替代方案**：录音时手动标注参与者名单，Assistant 在抽任务时
用「按语境推断 + 人工审批时确认负责人」。**审批环节反正要人看，
让人顺手确认负责人，比强行做说话人分离划算。**

### 4.4 语音 → 文档模板的衔接

现在是「出一坨转写文字」。要变成产品，需要：

```
转写稿 ──> 选模板 ──> 结构化文档
              ├── 会议纪要（议题/决议/待办）
              ├── 访谈笔记（Discovery 用，直接填 pain-inventory）
              └── 口述草稿（邮件/报价）
```

**「访谈笔记」这个模板优先做**——它是我们自己 Discovery 时每天要用的，
自己天天用的东西最不容易做歪。

## 5. 最小可用形态（演示级）

**一条端到端**：泰语会议录音 → 转写（标注语言段落）→ 会议纪要模板 → 交给 Assistant 抽任务。

**演示脚本**：
1. 当场录 2 分钟泰英混杂的对话
2. 展示转写，指出哪几段是泰语哪几段是英语
3. 出会议纪要
4. **说出评测数据**：「我们在类似环境测过 20 段，字符错误率大约 X%」
5. **指出局限**：嘈杂环境会明显变差；不区分说话人；**本地部署目前限 Apple Silicon Mac**（§7）

第 4 步是 Voice 区别于「随便一个转写 App」的地方——**有测过的数字**。

## 7. 🔴 平台限制：这一条要改对外文案

**[已核 2026-09-07]** 逐条查过上游产物，结论比「Apple Silicon 限定」这句**更窄也更准**：

**先说这张表证明了什么**：只证明「**在所查的 `v0.1.9` 与 `v0.2.6` 两个 tag 里，
官方预编译产物有哪些**」。它**不证明**任何平台上装得起来、跑得起来。

| 平台 | 官方 runtime 产物 | 我们能说什么 | 证据等级 |
|:---|:---|:---|:---|
| **Apple Silicon Mac**（M1+，macOS 11+）| ✅ `macos-arm64` | 有官方 `.app`，AgentEar 自述下载即用 | **[AgentEar 自述]** —— 我们没装过 |
| **Linux** x64 / arm64 | ✅ 四种变体 | 产物存在，但 app 壳是 macOS 的，**要我们自己组装** | **[待核]**，**不构成交付承诺** |
| **Windows** x64 | ✅ 含 CUDA / Vulkan | 同上 | **[待核]** |
| **Intel Mac** | ❌ 两个 tag 里都没有 | **没有官方预编译产物** | **[已核]**（仅此）；**能否自行编译 = [待核]** |

> ⚠️ **两句话收回**：原来写过「runtime 层是通的」和「Intel Mac 无解」。
> 前者把「有产物」说成了「能跑」，后者把「没有官方产物」说成了「不可能」。
> 这正是 `../../agent/architecture.md` §5 第 9 条那种绿灯 ——
> **断言的量纲对不上要抓的错误方向。**

### 对 `README.md` §5 例外条款的影响

原文写的是「数据敏感度高的客户，Voice 可以单独部署在他们机器上」。

**这句话现在只在两种情况下成立**：客户用 Apple Silicon Mac（开箱即用），
或客户有 Linux/Windows x64 机器且我们愿意付组装成本（未实测）。

**清迈的小生意用什么机器，BD 比 Dev 清楚 —— 但这条得先被知道，再决定怎么措辞。**
`README.md` §5 已经改过了，别再从旧版本抄那句话。
