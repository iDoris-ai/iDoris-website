# 新员工第一天上岗手册

> **你今天入职。这份文档的目标是：读完你就能开始干活。**
> 版本：v0.1 · 2026-09-05

## 0. 先花 20 分钟搞清楚我们是干什么的

**一句话**：我们帮泰国的中小企业、教育机构和本地服务业**把 AI 用进他们每天的活里**，
不逼他们重建现有流程。

**四个阶段**：Discover（找出该用在哪）→ Enable（教会员工用在自己的活上）→
Implement（真的做出来）→ Operate（保证它继续能用）。

**我们不是什么**：不是卖 AI 工具的，不是做网站 APP 的，不是卖便宜 token 的。

**最容易记住的一句**（对客户说的）：
> 「我们不是来劝您上 AI 的。我们花三天，把您公司里哪几件活一年花掉多少小时算给您看。
> 算完您觉得不值得做，我们也会直说。」

## 1. 三条全公司通用的规矩

**在读你自己的角色路径之前，这三条先记住。**

### 规矩一：每个事实要么 [已核] 要么 [待核]，没有第三种

对外材料里的任何数字、日期、政府流程、人名，
**要么我们自己点开原始来源核过（标 [已核]），要么标 [待核] 并写明去哪核**。

**为什么**：2026-09-05 我们在自己的定价页上栽过一次——
按页面自己的脚注推断某个模型「限时价已到期所以涨价了」，
改完之后表格、计算器、三处说明**全部自洽**，但集体错了：
厂商实际上把限时价扶正成了永久价。所有检查都是绿的。

> **一致性证明不了正确性。**

待核清单在 [`facts-to-verify.md`](facts-to-verify.md)。

### 规矩二：会说「你们现在还不该做这个」

我们卖的是判断力。一个会拒绝的供应商，下一次客户会先想到他。
明确不该卖的场景写在 [`services.md`](services.md) 每个服务档次的末尾，
以及 [`alternatives.md`](alternatives.md) §7 的六种不做的生意。

### 规矩三：客户的数据永不外流

客户的数据、内部流程、业务逻辑**永不进开源仓库、永不进公共样例**。
所有对外样例一律**虚构**。

## 2. 你是 BD（Business Development / Sales）

### 你负责什么

**把机会带进来，并判断它值不值得做。**

你有**否决权**（可以拒绝一个机会），但**没有承诺权**——
不能单独向客户承诺范围、工期、价格，必须过 PM 的可交付性回执。

**失败时的样子**：什么单都接，交付端被拖死。

### 你的第一周

| 天 | 做什么 |
|:---|:---|
| Day 1 | 读完必读五份（见下）；把资格判定的四条判据背下来 |
| Day 2 | 拿 `sample-discovery-hotel/` 走一遍，理解我们交付的到底是什么 |
| Day 3 | 用 `quote-template.md` 给一个虚构客户出一份报价单，找人 review |
| Day 4–5 | 跟一次真实的资格判定通话（听，不说）；之后自己打一个 |

### 你的必读五份（按顺序）

1. [`services.md`](services.md) — 我们卖什么，**以及什么情况下不该卖**
2. [`pricing.md`](pricing.md) — 价格区间**与取值判据**（第 2 节是重点）
3. [`alternatives.md`](alternatives.md) — 客户不买我们会怎样，我们怎么说
4. [`playbook-customer-journey.md`](playbook-customer-journey.md) — 全流程谁做什么
5. [`stage-gates.md`](stage-gates.md) — 门 1、门 2、门 3 是你的

### 你的第一个产出物

**一份填好的资格判定记录**，含：组织情况、联系人图谱（谁拍板/谁用/**谁会反对**）、
**客户自己说的痛点原话**、四条判据的判定结果。

### 遇到这些情况停下来问人

- 客户要求「先免费做一个试试」→ 标准答法在 `services.md` §0，
  但如果对方坚持，**不要自己让步**
- 客户要求「按人天报价」→ 答法在 `pricing.md` §5
- 客户是大型集团要集团级 AI 战略 → **不是我们的生意**，先问
- 对方要求我们借用某个 Digital Provider 的资质挂名 → **停下**，
  [待核] 这可能违规，见 `thailand-channels.md`

## 3. 你是 PM（Project Manager，泰语 native）

### 你负责什么

**把机会变成可交付的范围，并保证真的交付了。**

**你是唯一贯穿全程的 A。** 从 DiscoveryRunning 到 Operating，
任何时刻问「这个客户现在谁负责」，答案都是你。

**失败时的样子**：变成传话筒，两头都不担责。

### 为什么这个岗位是泰语 native 而不是工程师

瓶颈不在写代码（开源件已经很成熟），在于**访谈能不能听懂、
跟进能不能跟住、文档能不能让泰国客户看懂**。
反过来做会退化成「一个外国技术专家给泰国企业做项目」——不可复制。

### 你的第一周

| 天 | 做什么 |
|:---|:---|
| Day 1 | 读完必读五份；把 Discovery 的九项交付物背下来 |
| Day 2 | 通读 `discovery-sop.md` 全文，特别是 §5 三套访谈问题 |
| Day 3 | 拿 `sample-discovery-hotel/` 逐项对照，理解每项长什么样 |
| Day 4 | 用 `score.py` 跑一遍评分，理解分档判据 |
| Day 5 | 跟一次真实 Discovery 的 Day 1（观察 + 做转写整理） |

### 你的必读五份（按顺序）

1. [`playbook-customer-journey.md`](playbook-customer-journey.md) — 你的全景图
2. [`discovery-sop.md`](discovery-sop.md) — **你的主要工作手册，逐小时**
3. [`stage-gates.md`](stage-gates.md) — 门 2 的回执、门 3 到门 10 都是你的
4. [`services.md`](services.md) — 你要判断范围可不可交付
5. `discovery-skill/` 全部 — 访谈清单与模板

### 你的第一个产出物

**一份「范围可交付性回执」**（门 2）。哪怕只有一句话，也必须写下来。

格式：
> 「BD 承诺的范围是 X。我判断：可交付 / 不可交付，因为 Y。
> 若不可交付，建议改成 Z。—— 姓名，日期」

### 遇到这些情况停下来问人

- **拿不到决策层受访** → 推迟，不进场。**这是硬门槛，不要将就**
- BD 承诺的范围你判断交付不了 → **打回，不硬接**
- 客户不让看数据 → 应对方法在 `discovery-sop.md` §7.4，
  但要在交付物里标注「未经文档验证」
- Readiness ≤10 分但客户想上 L2/L3 → **照实说不该做**，不要迎合

## 4. 你是 Dev（Developer / FDE）

### 你负责什么

**把范围变成能跑的东西，并保证它还能继续跑。**

**你的输入永远是 PM 交出的**「工作流地图 + 用例 + 验收标准 + 数据边界」。
**你不直接从客户接需求**——那条路径一旦打开，范围就不可控了。

**失败时的样子**：做出很酷但没人用的东西。

### 你的第一周

| 天 | 做什么 |
|:---|:---|
| Day 1 | 读完必读五份；**把三条 License 红线背下来** |
| Day 2 | 读 `starter-kit/` 四份组件设计 + `gateway-design.md` |
| Day 3 | **做 Voice 现状盘点**（`starter-kit/voice.md` §1 的四个问题）|
| Day 4 | **验证 LangGraph 完全离线**（`oss-due-diligence.md` §1.2 的待核项）|
| Day 5 | 跑一遍 `score.py --self-test`，理解我们对「判据要能变红」的要求 |

### 你的必读五份（按顺序）

1. [`../agent/architecture.md`](../agent/architecture.md) — **八条不可破边界**
2. [`oss-due-diligence.md`](oss-due-diligence.md) — **License 红线与待核清单**
3. [`dev-plan.md`](dev-plan.md) — 分阶段实现路径
4. [`starter-kit/README.md`](starter-kit/README.md) — 四组件与共用契约
5. [`gateway-design.md`](gateway-design.md) — 所有组件的底座

### 三条 License 红线（**背下来**）

1. **ComfyUI 是 GPL-3.0，只能独立进程 HTTP 调用。**
   不 vendor、不 fork 进仓库、不 `import comfy`、不打进同一镜像。
   **任何 PR 引入 `import comfy` 一律拒绝合并。**
   越线后果：整个 iDoris Core 被传染成 GPL，**不可逆**。
2. **LiteLLM 的 `enterprise/` 目录另有许可**，绝不引用。
3. **模型权重的许可独立于代码。** 代码 MIT 不代表权重可商用。
   图像模型权重 [待核] 核清前 Creative 图像部分不对外交付。

### 你的第一个产出物

**Voice 现状盘点报告**。回答四个问题：
用的哪个 whisper 实现与模型尺寸 / 泰语是否单独调过 /
有没有可跑的 demo 入口 / 部署形态（本地还是云）。

**为什么是这个**：整个 Starter Kit 的演示计划建立在「Voice 已有基础」这个假设上，
而这个假设**从没被核实过**。不能在假设上继续叠设计。

### 遇到这些情况停下来问人

- 要引入一个新的开源依赖 → **先核 License**，写进 `oss-due-diligence.md`
- 客户/PM 要求「去掉人工审批，做成全自动」→ 见 `architecture.md` 边界五，
  **默认全审是设计不是懒**
- LangGraph 离线验证不通过 → **不要将就**，降级路径是自建状态机（2–3 天）
- 客户直接找你提需求 → 转给 PM，**不要直接接**

## 5. 第一周结束时，你应该能回答

不管你是哪个角色，这五个问题都该答得上来：

1. 我们的四个服务阶段分别做什么、交付什么？
2. 一个新客户从认识到签运维合同，中间有几道门？我负责哪几道？
3. Discovery 的九项交付物是什么？缺一项会怎样？
4. 我们明确不做的生意有哪些？
5. 遇到一个我不确定的事实，我该怎么处理？

**第 5 题的答案**：标 [待核]，写明去哪核，**不要猜，更不要写成 [已核]**。
