# iDoris Assistant — 审批队列

> 设计见 [`../../docs/business/starter-kit/assistant.md`](../../docs/business/starter-kit/assistant.md) §3.2 / §3.3
> 状态：**审批队列已完成**。LangGraph 流程编排尚未接入。

## 为什么先做这一块

**这是客户每天真正要用的东西。**

LangGraph 负责在「等人点头」这里停住并持久化；这个模块负责**人点头的那一下**。
前者是别人写好的库，后者是我们的业务规则与安全支点。

而且它**不依赖 LangGraph**（纯逻辑 + SQLite），所以可以先做、先测、先交付。

## 三条设计规矩

| # | 规矩 | 为什么 |
|:--|:---|:---|
| 1 | **草稿可编辑后放行** | 人改一半再发是最常见的路径。强制「要么全接受要么全驳回」会让人干脆不用这个系统——然后回到手工，我们省的那点时间就没了 |
| 2 | **必须显示来源** | **没有出处的草稿没人敢发。** 没有 `sources` 的草稿直接拒绝进队列 |
| 3 | **超时不自动放行** | 超时的后果是**升级提醒**，不是默认发出去。这与「默认全审」是同一个原则的两面 |

原始草稿与放行内容**分开存**（`body` vs `final_body`）——
出事时要能对比 AI 生成了什么、人改了什么。

## 自动放行是白名单，不是开关

`AutoReleasePolicy` **默认为空**。这不是配置疏忽，是设计。

一条规则要放行，四个条件全满足：`flow` 匹配 · 意图在白名单内 ·
置信度达标 · 不含个人信息。外加一个**随时可关的开关**。

> **一条错误的自动回复对本地小生意的伤害，远大于省下的那点人工。**
>
> 一家清迈酒店的 LINE 是他们的门面。回错一次房价、答错一次是否有空房，
> 损失的是真实订单和口碑。

**「价目」类意图明确不进白名单**，尽管它是最高频的问题之一——
**高频不等于低风险**。这条产品决策有专门的测试守着
（`test_price_intent_never_auto`）。

## 出网闸门：环境里有追踪配置就拒绝启动

P0 阻塞项 #1 的核查结论是：**风险不在库，在部署配置。**

socket 层实测：不设任何环境变量时 LangGraph **零次外部连接**；
但设 `LANGSMITH_TRACING=true` 时**确实会连** `api.smith.langchain.com`。

一台机器上多一个环境变量，客户的会议转写稿就开始往外发 ——
而且**日志照常、功能照常、测试照常绿**，不会有任何东西提醒你。

### 为什么是「拒绝启动」而不是「打警告」

打警告没人看。一条 WARNING 出现在容器启动的前两秒、后面还有几百行输出，
在真实运维里等于不存在。

而这件事的失败模式是**静默的数据外流**：出事时没人知道，
等发现的时候数据已经在别人的服务器上，撤不回来。

**启动不了，人一定会看；数据流出去了，人不一定会知道。**

### 为什么是前缀扫描而不是点名

点名一串已知变量看起来更精确，实际是**失败开放**：
langsmith 下个版本加一个新变量名，我们的清单不会自己长出来，于是静默漏过。

这里反过来 —— 扫 `LANGCHAIN_` / `LANGSMITH_` 前缀，**认不出来的一律拒绝**，
要放行必须显式写进 `KNOWN_HARMLESS` 并写清楚为什么。

误拒的代价是运维多看一行报错；漏放的代价是客户的会议记录出境。**不对称。**

### 两个方向的坏法后果完全不同

| 坏法 | 后果 |
|:---|:---|
| 永远拒绝 | Assistant 起不来 —— **运维五分钟内就会发现** |
| 永远放行 | 转写稿静默外流 —— **不会有任何人发现** |

所以测试两头都配了对照：脏环境必须拒绝，干净环境和**关掉的开关**必须放行。
（关掉的开关也拒绝的话，运维为了把服务起起来会去删配置管理里的整行，
下次就看不到「这里本来是显式关掉的」了。）

### 闸门必须真的被接上

`test_guard_is_actually_wired_into_the_entry_point` 直接检查入口文件里有那一句。

**一道没人调用的闸门等于不存在** —— 这是最容易白写的一类安全代码：
模块写得很漂亮、测试全绿、然后没有任何一条启动路径调用它。
这条测试写完的第一次运行就是红的，因为当时确实还没接上。

变异测试里也有对应的一条：「闸门从入口摘掉（模块还在，只是没人调用）」。

### 它管到哪为止

只管环境变量。**挡不住**：

- 代码里直接传 `callbacks=[LangChainTracer()]` —— 那是代码审查的事
- 别的库自己的遥测（各自另有开关）
- 环境干净但网络出口没关 —— 出网控制是部署层的事

**这是一道闸门，不是全部防线。** 写清楚它管到哪为止，
比让人以为「有这个就安全了」要紧。

### 部署脚本怎么用

    python3 egress_guard.py --check      # 退出码即结论，部署脚本不读人话

CI 里跑了三步：闸门自身的测试、**CI 环境本身的 `--check`**、
以及一条正对照 —— 在 `LANGSMITH_TRACING=true` 下演示必须启动失败。

## 怎么跑

```bash
python3 approval.py                # 烟测
python3 test_approval.py           # 完整测试（11 个测试函数）
./mutation_check.sh                # 变异测试 ← 最重要的那个
```

## 变异测试：十六条安全属性逐条验

**一个永远绿的测试套件，看起来和真测试一模一样。**

`mutation_check.sh` 逐条破坏出处强制、编辑放行、白名单默认为空、白名单开关、
置信度门槛、PII 拦截、超时语义、重复决策拦截、租户隔离、驳回理由强制，
断言测试**确实会变红**；再改一处无害的东西，断言**不会**误报。

> 写它的时候有一条变异**没有生效**：`[...] or (execute(...) and [])`，
> `or` 短路导致列表非空时 UPDATE 根本不跑，等于没破坏。
> 变异测试正确地报告了「这条属性没有被兜住」——**变异本身也要能变红**。
> 改成无条件生效后十条全绿。
>
> 这是本仓库第二次靠变异测试抓到自己写错的变异（第一次在 Gateway）。

## 每条断言都配负对照

| 正向 | 负对照 | 没有负对照会怎样 |
|---|---|---|
| 无 `sources` 被拒 ✓ | 有 `sources` 能进且正确保存 ✓ | 「什么都拒绝」也能全绿 |
| 编辑后放行生效 ✓ | 未编辑时原样放行 ✓ | 「永远用原文」也能全绿 |
| 超时项被列进升级 ✓ | 刚提交的**不**被列进 ✓ | 「全都算超时」也能全绿 |
| 四条件满足则自动放行 ✓ | 任一不满足都落回人工 ✓ | 「永远放行」也能全绿 |
| 查本租户有数据 ✓ | 查别的租户返回空 ✓ | 租户隔离形同虚设 |
