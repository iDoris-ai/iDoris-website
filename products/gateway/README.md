# iDoris AI Gateway — 路由策略引擎

> 设计见 [`../../docs/business/gateway-design.md`](../../docs/business/gateway-design.md)
> 状态：**最小可用形态的两块已完成**（路由决策 + 审计留痕）。模型调用尚未接入。

## 这两块做什么

| 模块 | 做什么 |
|:---|:---|
| [`routing.py`](routing.py) | 给定一个请求，决定它该走哪一档模型 —— 并且能说清为什么 |
| [`audit.py`](audit.py) | 记下每次调用的**元数据**，供客户看成本、我们做优化、出事能追溯 |

## 为什么这一段值得自己写

LiteLLM 解决的是「怎么调各家的 API」——**那是我们不该自建的部分**。

但「什么任务该走哪档、敏感数据必须留在本地、超预算怎么办」是**我们的业务规则**，
它必须是可读、可测、可审计的，不能埋在某个配置文件的深处。

## 三条不可破的规则

| # | 规则 | 为什么 |
|:--|:---|:---|
| 1 | `sensitivity=high` **必须**走 `local` 档，压过任务类型 | 隐私承诺的机械保障 —— **不能靠人记得在配置里写对** |
| 2 | 预算用尽**必须**拒绝，不是降级后继续跑 | 见过太多「预算告警」最后变成没人看的邮件 |
| 3 | 每次决策**必须**能说出 `reason` | 一个说不出理由的路由表，三个月后没人敢改 |

**规则 1 放在任务匹配之前**，所以无论路由表怎么写、有没有写这个任务，
敏感数据都不会出去。

**规则 2 放在规则 1 之前** —— 超预算时连敏感任务也不该跑，因为「跑」本身要花钱。

## 怎么跑

```bash
python3 routing.py --self-test     # 路由烟测
python3 test_routing.py            # 路由测试（10 个测试函数）
python3 audit.py                   # 审计烟测
python3 test_audit.py              # 审计测试（7 个测试函数）
./mutation_check.sh                # 变异测试 ← 最重要的那个
```

## 为什么有变异测试

**一个永远绿的测试套件，看起来和真测试一模一样。**

`mutation_check.sh` 逐条破坏**九条**规则，断言测试**确实会变红**；
再改一处无害的东西，断言测试**不会**误报。

十条全过，前面那些绿灯才是可信的读数。

> 写这个脚本时它先抓到了**我自己写错的变异**：一条 sed 表达式生成了
> `frozenset({}) or frozenset({...})`，求值成后者，等于没破坏。
> 变异测试连「变异本身是不是真的破坏了」都验 —— 这正是它的价值。

> 这条纪律来自本仓库 2026-09-05 的教训：在 `/pricing` 上按推断改了价格，
> 改完后表格、计算器、三处说明全部自洽——但集体错了。所有检查都是绿的。
> **一致性证明不了正确性。**

## 每个测试都配了负对照

不只测「该拦的拦住了」，还测「不该拦的没拦」：

- `sensitivity=high` 走 local ✓ **且** `normal` 的同一任务不走 local ✓
  （否则「什么都走 local」也能让测试全绿）
- 超预算拒绝 ✓ **且** 预算充足时正常放行 ✓
  （否则「永远拒绝」也能全绿）
- 非法配置被拒 ✓ **且** 合法配置能过 ✓
  （否则「什么都拒绝」也能全绿）
- 90% 时 `premium` 降级 ✓ **且** 同时 `mid` 不动 ✓

## 配置

见 [`policy.example.json`](policy.example.json)。两条要点：

- **`tiers` 里放的是模型列表不是单个模型。** 模型会下线、涨价、被更好的取代——
  这里是唯一需要改的地方，业务代码永远只说 tier 名。
- **具体型号故意留空。** 模型换代极快，写死在示例里三个月就过期；
  部署时按实际填，选型依据看 `/pricing` 页的牌价表。

## 审计的那条不可破边界

> **Gateway 绝不存储客户业务数据的内容，只存元数据。**

存：时间、租户、用户、组件、任务、敏感度、tier、模型、token 数、成本、延迟、成败。
不存：提示词、模型输出、上传的文档、任何客户业务数据。

**理由**：Gateway 是我们托管的、**跨客户**的组件。一旦它存内容，
它就成了一个集中的客户数据库 —— 那是我们最不想承担的责任。

这条边界由 `_FORBIDDEN_FIELDS` **机械保证**：出现任何疑似内容的字段名
（大小写不敏感）直接拒绝写入；自由文本字段超过 500 字符也拒绝 ——
字段名合法不代表内容合法。**不是「记得别传」，是闸门。**

`AuditRecord` 是 frozen dataclass，字段固定，这是第一道防线；
`assert_no_content` 是第二道。两道都有变异测试兜住。

### 隐私的事后核查

`sensitive_calls_off_local()` 找出所有 `sensitivity=high` 却没走 `local` 的调用。

**正常情况下它必须永远返回空** —— 路由引擎的规则 1 保证了这一点。
它非空就说明有人绕过了 Gateway 直连模型，或者规则 1 被改坏了。

事前拦截（路由）+ 事后核查（审计）= 双保险。

## 还没做的

按 `gateway-design.md` §7 的最小可用形态，剩下一块：**接入 LiteLLM 真正发请求**。

**明确不做**（等有真实用量再说）：成本闸的告警通道、BYOK、premium 档的实际接入。

存储用 SQLite。第一批客户每天几百到几千条调用，SQLite 完全够用 ——
**少一个要运维的东西**比多一点写入性能重要得多。撑不住再换，
换的成本远低于现在多养一个 Postgres。
